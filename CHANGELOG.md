# Changelog

All notable changes to this project are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project will follow [Semantic Versioning](https://semver.org/) once it has a release.

## [Unreleased]

### Added

- Labour estimates on every surface. `GET /v1/jobs` and `/v1/jobs/{job}` give the job list and one job with what it includes and excludes. `GET /v1/vehicles/{id}/labor`, `/labor/{job}` and the same under `/v1/vin/{vin}` give, for each job, Wenmar's estimate of the hours: low, typical and high, its `basis` (`expert` or `observed`) and the `scope` that answered (`engine`, `generation`, `model` or `class`), so a figure for a class of vehicle is never shown as if it were worked out on one vehicle. The overview's `labor` block is filled where the estimates are held. The MCP tool `wenmar_labor` (actions `jobs`, `vehicle`, `vin`), `wenmar-open labor jobs|job|vehicle|vin`, the npm client (`jobs`, `job`, `labor`, `vinLabor`) and `wenmar-open/offline` give the same answers. Every answer carries `Labour estimates by Wenmar Pro, CC BY 4.0` and "An estimate, not a quote. Rust, seized fasteners and added equipment change the time."; none holds a price. No shop file holds estimates yet.
- `open-data build-shop` builds a hand-kept dataset of labour estimates: `labor`, from `data/labor/*.yaml`, one file per job of `data/jobs.yaml`. An estimate is a low, a typical and a high number of hours for a scope: a class of vehicle, a model, a run of model years, or one engine. A lookup takes the narrowest scope that has a figure and says which it was. Each model year's class comes from EPA's size class, mapped to 13 classes, or from the nearest rated model year of the same model. The dataset is under CC BY 4.0 with the credit `Labour estimates by Wenmar Pro, CC BY 4.0`; the rest of the data and the code keep their licences. Estimates are written by people who do the work and never taken from a labour guide. The directory starts with no estimate, so no shop file holds the dataset yet; nothing serves it yet.
- `data/jobs.yaml`: the list of repair jobs a labour time can be about, each with a permanent id (`brake-pads-front`), a name, its system, the components it acts on, what it includes and excludes, and related jobs. It starts as a draft of 22 ids and names; what each job covers is still to be written by a person who does the work. `open-data build-shop` checks the file in every build and builds the `jobs` dataset (`job`, `job_component`) once the list is marked reviewed. Nothing serves it yet. Wenmar Pro is to record repair orders against these ids.
- Trouble code pages. `/codes` lists every described code by system, with a search box that needs no JavaScript. `/codes/{code}` is one code: what it means, common causes, what to check first, the components it concerns and related codes, marked up as a `DefinedTerm`. `/makes/{make}/{model}/{year}/codes/{code}` is a code on one model year: the description, the bulletins of that model year that name the code, and the bulletins and recalls about the same components; it answers for any code and is offered to search engines only when it has a bulletin or a recall to show. Each has a Markdown twin. A bulletin's page links the codes it names that are described, and a model year's bulletin list narrowed to a code links that code's page for the vehicle. `/sitemaps/codes.xml` lists the described codes.
- Trouble codes. `GET /v1/codes/{code}` gives one generic OBD-II code as this project describes it in its own words: title, meaning, common causes, first checks, the components it concerns and related codes. `GET /v1/codes?q=&system=` lists the described codes. `GET /v1/vehicles/{id}/codes/{code}` takes any code, a manufacturer-specific one included, and gives the description (or `null`), the bulletins of that model year whose NHTSA summary names the code, and the bulletins and recalls of that model year about the same components. The MCP tool `wenmar_codes` (actions `get`, `search`, `vehicle`), `wenmar-open codes get|search|vehicle`, the npm client (`code`, `codes`, `vehicleCode`) and `wenmar-open/offline` give the same answers. Bulletins are on the hosted service only, so from files the two bulletin parts are `null`. No shop file holds code descriptions yet: until records are written, the first two routes answer `dataset_unavailable` and the third answers with `description: null` where bulletins are held.
- `open-data build-shop` builds a hand-written dataset from the repository itself: `codes`, from `data/codes/*.yaml`. A record is one generic OBD-II trouble code described in this project's own words: a title, a meaning, common causes, first checks, the components of `data/components.yaml` it concerns, related codes, and who wrote it, who reviewed it and when. Only the ranges every maker uses the same way may have a record (`P0`, `P2`, `P3400` and up, `B0`, `C0`, `U0`, `U3`); the build refuses any other code, a component or a related code that does not exist, and a record its author reviewed. The directory starts with no record, so no shop file holds the dataset yet; nothing serves it yet.
- Fuel consumption ratings, specifications, fluids and tire fitments everywhere the recalls are. MCP: `wenmar_vehicles` and `wenmar_vin` each have the actions `fuel`, `specs`, `fluids` and `tires` (and the argument `country` for fuel), at `/mcp` and in `wenmar-open mcp`. `wenmar-open vehicles fuel|specs|fluids|tires <id>` and `wenmar-open vin fuel|specs|fluids|tires <vin>` answer from the hosted API or from the shop data file with the same JSON. `wenmar-open/offline` (npm) has `fuel`, `specs`, `fluids`, `tires`, `vinFuel`, `vinSpecs`, `vinFluids`, `vinTires` and `complaints`. The overview's `fuel`, `specs`, `fluids`, `tires` and `complaints` blocks are filled from files as the hosted API fills them. `/llms.txt` and `/docs` give the addresses a server holds. `wenmar-shopdata`: the module `answer::facts` builds these answers from files.
- A reference table of battery group sizes: `data/reference/battery-groups.toml` holds the length, width and height of each group's case and where its terminals are, each read from a named source, and the server's build refuses a malformed file and converts between millimetres and inches itself. Its page, `/guides/battery-group-sizes`, says what a group size is and that it does not say which group fits which vehicle. The table holds no group yet and is not confirmed, so the page is a draft that nothing serves or lists.
- Links to a model year's owner's manual and maintenance schedule on the maker's own site. A fluids file in `data/fluids/` may carry a `manuals` list (`kind`, `url`, `checked`, `reviewer`), which `open-data build-shop` builds into the dataset `manuals`; a make in `data/catalog/makes.yaml` may carry `manual_url_template` and `maintenance_url_template`, an address with `{year}` and `{model}` in it, for makers whose addresses follow a pattern. The model-year page and its Markdown show them under "Owner's manual and maintenance schedule": a link a person opened with the day it was checked, or else the address made from the pattern, said to be one nobody opened. No manual is downloaded or kept. No link is recorded yet.
- `open-data check-links` and `mise run check-links` (`bin/check-links`) ask for every stored link, one at a time with a pause, and write `data/build/link-report.md`: dead links (the server answered 404 or 410), links that answered at another address, and links that could not be checked because the server refused a script or did not answer. It never fails because a link did.
- `open-data hand-coverage --catalog <data file>` lists the makes in the order of `data/catalog/makes.yaml` and, for each, how many of its models have hand-read fluid or tire records and which have none. `data/fluids/README.md` has the steps for entering a record.
- Fluids and tire fitments read by hand, on a server whose shop file holds them. `GET /v1/vehicles/{id}/fluids` and `GET /v1/vin/{vin}/fluids` keep EPA's `engine_oil` grades as they were and gain `checked_as_of` and five lists, `engine_oil_checked`, `transmission`, `coolant`, `refrigerant` and `brake`: each record has its `source`, the day it was `checked`, and capacities and charges in both units with `capacity_written_in` or `charge_written_in` naming the one the document printed. The routes now answer when the server holds either the oil grades or the records. New: `GET /v1/vehicles/{id}/tires` and `GET /v1/vin/{vin}/tires` list every original-equipment size on record with its trims, cold pressures, wheel nut torque and bolt pattern; a VIN's list is never narrowed. The overview's `fluids` block carries the same lists and its `tires` block is filled. The model-year page and its Markdown show one "Engine oil" table with EPA's grade beside what was read from the maker's document, an "Other fluids" table and a "Tires and wheels" table; every figure is followed by its source, its day and a "Report an error" link that names the figure. A model year with no record shows nothing in its place.
- `wenmar-open` (npm): `tires(id)` and `vinTires(vin)` on the hosted client, and the types `VehicleTires`, `VinTires`, `TireFitment` and `FluidRecord`.
- `open-data build-shop` builds two hand-kept datasets from the repository itself: `fluids`, from `data/fluids/*.yaml` (engine oil grade, specification and capacity by engine; transmission fluid, coolant, refrigerant and brake fluid), and `tires`, from `data/tires/*.yaml` (every original-equipment size of a model year with its trims, cold pressures, wheel nut torque and bolt pattern). Every record names the document it was read from, the day and the reviewer. A figure is written once in the unit the source prints, and the build works out the other unit exactly. The build refuses a record for a vehicle or an engine the catalog does not have, an unknown unit and a record without a source. Both directories start with no record, so no shop file holds the datasets yet; nothing serves them yet.
- What owners report, on a server or a shop file that holds complaints. `GET /v1/vehicles/{id}/complaints` gives a model year's complaints to NHTSA as counts: the total, how many report a crash, a fire or an injury, the median mileage owners gave (kilometres and miles), and each component with at least five complaints. The overview answers have a `complaints` block with the same in brief. The model-year page has a section "What owners report" when there are at least five. The MCP tool `wenmar_vehicles` has the action `complaints`, and the command-line tool has `wenmar-open vehicles complaints <id>`, from the local shop file or the hosted API, with the same JSON. The offline npm package and its engine do not have complaints yet: the engine is at its size budget. Every one says these are owners' reports, not verified and not defects, and that a count is not a rate. No complaint text, place, VIN or name is held anywhere.
- Website, on a server that holds bulletins: the model-year page has a section "Maintenance updates from the manufacturer" when a bulletin for that model year mentions a maintenance schedule or a service interval. It lists up to five, newest first, each with NHTSA's summary, a link to its page and to NHTSA's copy of the document, then a link to all of them and, where one is on file, to the maker's own maintenance schedule. It says the bulletins are not the schedule itself. The Markdown version has the same list.
- Website: a recall campaign's page lists the bulletins for the same vehicles and component, as a bulletin's page lists recalls; a model year's recall list and bulletin list link each other; and the model-year page names the models it "shares campaigns and bulletins with", worked out at build time from the documents that list both (at least five, and a fifth of the model year's own) and marked as not meaning that a part fits both.
- Bulletins everywhere recalls are, on a server that holds them. The overview answers (`/v1/vehicles/{id}/overview`, `/v1/vin/{vin}/overview`) have a `bulletins` block: the count, the count by type, the three newest and the address of the list; `/v1/models/{make}/{model}` gives each model year's bulletin count. The model-year page has a "Bulletins" line and the VIN result page a section with the newest three. MCP has a fourth tool, `wenmar_bulletins`, with the actions `vehicle`, `vin`, `get` and `search`. The command-line tool has `wenmar-open bulletins vehicle|vin|get|search`; bulletins are answered by the hosted API only, because the shop data file that is downloaded does not hold them.
- `data/components.yaml`: a first list of components, 24 systems and 78 parts a job acts on (`brake-pad`, `water-pump`), each with the NHTSA component paths and Transport Canada system names it covers. It is a draft awaiting review. `open-data build-shop` records which components each recall and each bulletin is about (`recall_component`, `bulletin_component`), the trouble codes each bulletin's summary names (`bulletin_code`; 61,445 on the files of 2026-10-11) and the bulletins about a maintenance schedule or interval (`bulletin_topic`). Nothing serves these yet.
- `open-data build-shop` takes `--nhtsa-mfr-comms`, the directory `open-data fetch nhtsa-mfr-comms` wrote. It adds the dataset `bulletins` (NHTSA manufacturer communications, public domain): one `bulletin` row for each communication with NHTSA's summary, and the vehicles each lists stored as runs of model years (1.4 million rows for 4.35 million vehicles). Bulletins add 144 MB, so only the hosted service carries them: `--offline-out <path>` writes a second shop file without them, and `bin/shop-data` writes it to `data/build/shop/offline/`. `open-data coverage` measures bulletins, and `data/coverage.yaml` holds their first minimum. Nothing serves the data yet.
- A shop data release now has two shop files. `wenmar-open-shop-YYYY.MM.DD.sqlite3.gz`, the name every release has had, is the offline file, without bulletins: `wenmar-open data pull --shop` and the npm package `wenmar-open-data-shop` take it, as before. `wenmar-open-shop-full-YYYY.MM.DD.sqlite3.gz` is the full file, with bulletins, and `bin/shop-pull` takes it for the server's image, storing it under the name the image already copies. The manifest keeps its seven fields, which describe the offline file, and gains `full` (`bytes`, `sha256`, `datasets`) for the full one. `scripts/shop-datasets-check.mjs` compares each file with its own kind. `scripts/shop-manifest.mjs` and `clients/data-shop/scripts/prepare.mjs` refuse a file that holds a hosted-only dataset where the offline file belongs. The release workflow fetches `nhtsa-mfr-comms` and measures coverage on the full file.
- Crash test ratings everywhere. MCP: `wenmar_vehicles` has the action `safety` (a vehicle id), which gives what `GET /v1/vehicles/{id}/safety` gives: every rating NHTSA gave a vehicle of the model year, by body style and drive, none picked. `wenmar-open vehicles safety <id>` answers from the hosted API or from the shop data file with the same JSON, field for field; at a terminal it is text in NHTSA's own words for each vehicle. `wenmar-open/offline` (npm) has `safety(id)`. Without the ratings each fails with `dataset_unavailable`, naming `ratings`; the command-line tool adds `Run: wenmar-open data pull --shop`. `/llms.txt` and `/docs` give the address on a server that holds the ratings.
- The `safety` block of an overview from files: `wenmar-open vehicles overview`, `vin overview`, their MCP actions and the offline npm client's `overview` and `vinOverview` carry the crash test ratings when the shop file holds them, as the hosted API does, and `null` when it does not.
- The overview answers everywhere. MCP: `wenmar_vehicles` has the actions `overview` (a vehicle id) and `model_years` (a make and a model), `wenmar_vin` has `overview` (a VIN), and `wenmar_recalls` has `recent` (`since`, a day); each answer is what `GET /v1/vehicles/{id}/overview`, `/v1/models/{make}/{model}`, `/v1/vin/{vin}/overview` and `/v1/recalls/recent` give. No tool was added. `/llms.txt` names the actions and `/docs` has a section, "Everything for one vehicle", with the addresses.
- `wenmar-open vehicles overview <id>`, `vin overview <vin>`, `vehicles model-years --make --model` and `recalls recent --since <day>`, from the hosted API or from local files with the same JSON. From local files `lookup.maker` and `links.maker` are always `null` and every address points at `https://open.wenmarpro.com`. An overview and a model's years answer with no shop data file: `recalls` is then `null`. From files, and offline in the npm package, the `specs`, `fuel`, `fluids` and `safety` blocks of an overview are `null` for now: only the hosted API fills them. `recalls recent` needs it, and says `Run: wenmar-open data pull --shop` without it. At a terminal an overview is text that says how many recall campaigns may apply and where to check the VIN. Nothing says a recall applies to a VIN.
- `wenmar-open/offline` (npm): `overview(id)`, `vinOverview(vin)`, `modelYears(make, model)` and `recentRecalls({ since })`, with the hosted client's signatures and answers. The first three answer with no shop store, with `recalls: null`. `decodeVins` offline still takes no `include`.
- `wenmar-shopdata`: `answer::Overviews` builds the overview of a model year and of a VIN and the model years of a model from the core data file, with a shop file or without one, and `Answers::recent` the campaigns reported since a day. Tests hold them to the API's JSON through the command-line tool and through the offline engine.
- A parts-ordering card for a VIN. `GET /v1/vin/{vin}/parts-card` gives what a parts counter asks for, one line each with its source: model year, make, model, trim, body, drive, transmission, engine, displacement, cylinders, fuel and plant from the decode; the eighth and eleventh characters of the VIN; the catalog engine and its eighth-character code when the decode settles the engine; the emission standard and EPA sales area when EPA's file was matched to that engine; and the build dates a recall campaign names for the model year. Nothing is guessed, and a build-date line is the range a campaign covers, not the vehicle's own build date. `text` is the card ready to paste. The VIN result page shows the card as text that can be selected with no JavaScript, with a copy button. `wenmar-open` (npm) has `partsCard(vin)`.
- API: manufacturer communications from NHTSA (service bulletins, service campaigns, warranty extensions, over-the-air updates), on a server run with a shop file that holds them. `GET /v1/vehicles/{id}/bulletins` lists those of a model year, newest first, one page at a time, with `counts` of every type, component, trouble code and topic among them; `GET /v1/vin/{vin}/bulletins` does the same for the model year a VIN decodes to; `GET /v1/bulletins/{nhtsa_id}` gives one with every vehicle it lists, the components it is about and the trouble codes its summary names; `GET /v1/bulletins` lists and searches them all. Each list takes `type`, `component`, `code`, `topic`, `q`, `limit` and `cursor`. An answer holds NHTSA's summary, never the document: `document` gives the two addresses NHTSA's copy may be at, marked as not confirmed, or `null` for a communication received before July 2017. A server with no bulletin data answers these routes 404 `dataset_unavailable`.
- `wenmar-open` (npm): `bulletins(id)`, `vinBulletins(vin)`, `bulletin(nhtsaId)` and `searchBulletins(query)` on the hosted client, with their types.
- Website: bulletin pages, on a server run with a shop file that holds bulletins. `/makes/{make}/{model}/{year}/bulletins` lists a model year's manufacturer communications from NHTSA, 25 a page, newest first, with warranty extensions in a table of their own at the top and links that narrow the list by type, component, trouble code and topic. `/bulletins/{nhtsa_id}` shows one: the vehicles it lists, its type, components and the trouble codes its summary names, NHTSA's summary, a link to NHTSA's copy of the document, and the recalls and other bulletins for the same vehicles and component. `/bulletins` has the VIN box, the picker and the newest. The first two have Markdown versions at the same address with `.md`. The documents belong to the manufacturers and are linked, never held. `/sitemap.xml` lists a `bulletins-{year}` sitemap for each year NHTSA published bulletins in (split in parts of 50,000 if a year passes that) and a `model-bulletins-{year}` sitemap for each model year with a list.
- Recall completion: `open-data fetch nhtsa-recall-reports` downloads NHTSA's recall quarterly and annual report files, and `open-data build-shop --nhtsa-recall-reports <dir>` adds the dataset `recall_reports`: for each NHTSA vehicle campaign with a report, the newest one the manufacturer filed. `GET /v1/recalls/{source}/{campaign}` has a new field, `completion`: the vehicles involved, remedied, unreachable and removed, `remedied_percent`, and the period the report is for. It is `null` for a Canadian campaign, for a campaign with no report and on a server without the dataset. The campaign's page and Markdown show it under "Remedy progress the manufacturer reported", the `wenmar_recalls` tool carries it, and `wenmar-open recalls campaign` prints it. The figures are totals for the whole campaign at the end of the period named, which may be years past; they say nothing of one vehicle.
- NHTSA defect investigations, on a server run with a shop file that holds them. `open-data fetch nhtsa-investigations` downloads NHTSA's file and `open-data build-shop --nhtsa-investigations` adds the dataset `investigations` (public domain): every investigation, the vehicles it lists matched to the catalog, and the recall campaigns it led to. `GET /v1/vehicles/{id}/investigations` lists the open investigations that list a model year, and `GET /v1/recalls/{source}/{campaign}/investigations` the ones that led to a recall. The model-year page and a VIN result page say "Under investigation by NHTSA" when an open investigation lists the model year; a recall campaign's page says "Investigated as" with the action numbers. Every one of them says that an investigation is not a finding of a defect. On a server without the dataset every page is unchanged.
- `wenmar-open` (npm): `investigations(id)` and `recallInvestigations(source, campaign)` on the hosted client, with their types.
- `wenmar-open/offline` (npm): recalls with no network. `new WenmarOpenOffline({ store, shop })` takes a second store that holds the shop file, and `recalls(id)`, `vinRecalls(vin)`, `recall(source, campaign)` and `searchRecalls(query)` give what the hosted client gives, with one difference: `lookup.maker` is always `null`. Every answer has `may_apply: true` and the official lookups; nothing says a recall applies to a VIN. Without a shop store the four fail with `dataset_unavailable`. `openOffline()` uses the shop file of `wenmar-open-data-shop` when that package is installed, or `{ shopPath }`; a shop file that does not go with the data file is refused with `data_invalid`. `meta().datasets` lists what the shop file holds. `Statement` has an optional `db`, `"shop"` for a statement of the shop file.
- A new npm package, `wenmar-open-data-shop`: the shop file (recalls from NHTSA and Transport Canada) as one SQLite file, about 17 MB to download and 77 MB on disk. Its version is `<schema>.<YYYYMMDD>.<rebuild>`, such as `1.20261012.0`, and it names the exact `wenmar-open-data` version it goes with as a peer. `wenmar-open` names it as a second optional peer, `^1.0.0`.
- `wenmar-open recalls vehicle <id>`, `recalls vin <vin>`, `recalls campaign <source> <campaign>` and `recalls search`: the recall campaigns from NHTSA and Transport Canada that may apply to a model year, one campaign with every vehicle it lists, and the list of campaigns. They answer from the hosted API or from local files with the same JSON, with one difference: from local files `lookup.maker` is always `null`. At a terminal the answer is text that ends by saying a recall listed may apply and where to check the VIN. Nothing says a recall applies to a VIN.
- `wenmar-open data pull --shop` downloads the shop data file, which holds the recalls, beside the data file: the newest one published that was built against the data file in place. `wenmar-open data status --shop` says what is there. A shop file goes with one data file; one that does not is refused with `data_invalid` and the tool says to pull again. Without a shop file the recall commands fail with `dataset_unavailable` and `Run: wenmar-open data pull --shop`.
- `wenmar-shopdata`: the module `answer` builds recall answers in the API's words from a shop file and the core data file's catalog, over any `Source`.
- `wenmar-open` (npm): the README has a section on recalls, with examples that are compiled; `dataset_unavailable`, the `404` a server with no recall data answers, is one of `ApiErrorCode`, and `details.dataset` names what is missing.
- MCP: a third tool, `wenmar_recalls`, at `/mcp` and in `wenmar-open mcp`, with the actions `vehicle` (a vehicle id), `vin`, `campaign` (a publisher, `nhtsa` or `tc`, and a campaign number) and `search`. Each answer is what the matching recall route of the API gives: recall campaigns that may apply to a year, make and model, with `may_apply: true` and the official lookups where a VIN can be checked. Nothing says a recall applies to a VIN. A server with no recall data answers the tool with an error result carrying the API's `dataset_unavailable` error. `wenmar-open mcp` answers it from the hosted API; from the local data file it answers `dataset_unavailable` and says to run `wenmar-open data pull --shop`.
- Pages on what the law asks of a repair shop in each Canadian province and territory, at `/rules/canada` and `/rules/canada/{code}`: written estimates, authorisation, going over an estimate, warranty, invoices, old parts, winter tires, inspections and environmental fees. Every rule is in `data/rules/canada.toml` with its source and the day it was read, the build refuses a malformed file, and a province shows nothing until every topic has a source. No province is filled in yet: each page says "Not yet checked".
- The wire gauge calculator, at `/tools/wire-gauge`: the voltage drop of each gauge for a current and a length at 12 V or 24 V, and the thinnest wire that stays within the drop allowed. The resistance of each gauge is in `data/reference/wire-resistance.toml` with its source and the day it was read; until it is checked the page says "Not yet checked" and works nothing out.
- `data/catalog/makes.yaml` can record links to a maker's own pages: recall lookup, owner's manuals, maintenance schedules, service information, parts catalogue and customer line, with the day they were checked. The make page and every model-year page of that make show them, as do their Markdown versions and the new `GET /v1/makes/{make}`. The links are compiled into the server; the data file is unchanged.
- `open-server`: the optional setting `OPEN_SHOP_DATA` names a shop file to serve beside the data file. The server refuses to start over a shop file of another schema version or one built against a different data file, and says which. `GET /v1/meta` has a new field, `datasets`: the datasets the server holds, by id, each with `as_of`, `rows`, `licence` and `attribution`; it is `{}` when there is no shop file, and always `{}` in the npm package's offline mode. A new error code, `dataset_unavailable` (HTTP 404), is what a route for a dataset the server lacks will answer; no route uses it yet. The `ETag` of a server with a shop file also carries the shop file's version.
- `open-data fetch` takes a source. `fetch` and `fetch vpic` are unchanged. `fetch nhtsa-recalls` and `fetch tc-recalls` download NHTSA's and Transport Canada's recall files to `data/build/sources/<source>/` and write a `source.json` there recording each file's address, its `Last-Modified` header and the time fetched. Nothing reads these files yet.
- `open-data build-shop --catalog <data file> --out <shop file>` creates a shop file: a second SQLite file, `wenmar-open-shop-YYYY.MM.DD.sqlite3`, that will hold recalls and other datasets matched to the catalog of the data file it was built against. For now it holds only its `meta` table, with no datasets. `bin/shop-data` builds one into `data/build/shop/`. The data file itself is not changed.
- `open-data build-shop` matches a source's make and model names to the catalog: by name, then by the longest catalog model the name starts with (`SILVERADO 1500` is `Silverado`), then through the new curated file `data/shop/models.yaml`, where a family name such as BMW `3 SERIES` lists its models. A model matches only for a model year the catalog has it in. Rows that match nothing are kept with the source's own text. No dataset uses it yet.
- `open-data coverage --shop <shop file> --catalog <data file>` reports how much of each dataset in a shop file matched the catalog, by kind of match, with the 25 commonest unmatched names, measured over light makes and model years from 2000. It fails below the minimums in the new `data/coverage.yaml`; `--write` records new ones. `bin/coverage` runs it on the newest files. No dataset has rows to measure yet.
- Website: the VIN result page and every model-year page (and its Markdown version) link to a GitHub issue form already filled in with the page and the vehicle. ## [0.2.0] - 2026-10-10

### Added

- `wenmar-open` npm package: the offline mode, `wenmar-open/offline`, which decodes a VIN in the consumer's own process with no network. The decoder is the same Rust code as the crates, compiled to WebAssembly; the data is read through Node's own SQLite, a Cloudflare D1 store, or any SQLite store the caller supplies.
- `wenmar-open-data` npm package: the data file as an npm package, so the offline mode has something to read. Its version is its schema version, the year and month of the data, and a rebuild number, so `^3.202609.0` takes every later month and never a file this decoder cannot read.
- `bin/release`: the monthly release, run by hand on the 10th. It refuses unless `main` is clean, pushed and green in CI; bumps every version, cuts the changelog and records the data version in `config/deploy.yml` through `scripts/release-bump.sh`; then runs `scripts/release-check.sh`, commits and tags, and prints the two pushes to run. It pushes nothing itself and stores no secret. `scripts/release-test.sh` and `scripts/release-bump-test.sh` test it, and CI runs both.
- `.github/workflows/monthly-release.yml` does the same thing unattended on the same schedule. It is written and checked but not switched on; see "The monthly release" in `docs/releasing.md`.

### Changed

- `open-server` reads the data file through `rusqlite`, and its free-text search index is built over SQLite's FTS5 instead of turso.
- `open-server`: a free-text search for light vehicles could return fewer results than asked for. The search index fetched four times the requested rows and discarded the ones outside the scope, hoping the discarded ones left room — but only 11% of the 31,470 models in the index are light, so a query matching many heavy models could fill that window before a light one appeared. The scope is now applied in SQL and the limit is what the caller asked for. The same over-fetch was in place before, through turso.
- `wenmar-open-turso` is replaced by `wenmar-open-db`, the same library over `rusqlite`. Nothing a consumer of the crate wrote needs to change beyond the dependency: the names and signatures are the same (`Db`, `DbError`, `Meta`, `Worker`, `Decode`), the data file is still opened read-only, and `TursoSource` is gone in favour of `wenmar_vehicles::sqlite::SqliteSource`. `wenmar-open-turso` must be yanked on crates.io when this is released; crates.io keeps the version either way, and only a yank stops new dependents.

### Removed

- The `turso` dependency, and with it the tantivy tree it carried: about 2 GB of build output and 2,114 lines of `Cargo.lock`. The bundled SQLite that `rusqlite` compiles has FTS5 and honours SQLite's file locks.

### Fixed

- `open-server`: the MCP endpoint also answers at the site's own address and at `/mcp/`. Claude's custom connector dialog was given `https://open.wenmarpro.com`, got `405` for its first message, took that for a sign-in prompt and failed to register with a sign-in service that does not exist.

### Internal

- Tests that decode a VIN from a clean install of the *packed* npm tarballs, so a release that left the offline mode out of its tarball fails before it is published rather than after. This is what 0.1.0 did: its tarball carried the hosted client only.
- `release-check`: `server.json` is checked against the version like every other file that records it. It is asserted against the build by a test but was in neither the runbook nor the check, so it went stale without complaint.
- `release-check`: the crate it would publish is `wenmar-open-db`, and it checks that the `wenmar-open-data` manifest still ships the data file and that `scripts/prepare.mjs` still gives the published manifest its version from the data file's own meta table, so a placeholder version cannot reach npm unnoticed.
- `bin/release-data`: the `wenmar-open-data` npm package, made from a checkout instead of through the Actions interface. It finds the newest `data-YYYY.MM` release, checks the file against the SHA256 that release published, assembles the package with `clients/data/scripts/prepare.mjs`, and then verifies it: it packs the package, installs the tarball into a scratch directory and reads the data file's own meta table back out. A package carrying no data file — which is what `0.0.1` on npm is — is refused there rather than after it is published. It publishes nothing and pushes nothing: it prints the `npm publish` to run. `scripts/release-data-test.sh` tests it, and CI runs it.
- `bin/release` waited for nothing. It read CI once and refused while a run was still going, so a release started just after a push always failed and had to be started again. It now polls every 30 seconds for up to 30 minutes, printing the run's URL while it waits. A red run, or one still going after 30 minutes, refuses exactly as before.
- The `npm publish` that `bin/release-data` prints no longer carries `--provenance`. npm only makes a provenance statement for a publish coming from GitHub Actions or GitLab CI, and refuses anywhere else with `Automatic provenance generation not supported for provider: null` before publishing a byte. The workflow path — the `npm` job of `data-release.yml` — still does, and is the way to publish with provenance.
- The npm fixtures record the version like every other file that does, and nothing read them. `clients/js/test/fixtures/offline-cases.json` answers with `server_version`, which is `CARGO_PKG_VERSION` baked in when the crate is compiled, so a version change without regenerating it left a fixture that answered with the old version — caught by CI, one commit later than it should have been. `release-bump.sh` now regenerates the fixtures as part of the bump, touching the wasm source first so cargo really rebuilds it, and `release-check.sh` fails a release whose fixture disagrees with `Cargo.toml`.

- `wenmar-open-turso` crate: opens a data file read-only through `turso`, decodes a VIN and reads the catalog from async code without blocking the runtime. It is the server's own data access, moved into a library.
- `open-server` reads the data file through `wenmar-open-turso`. Its behaviour is unchanged.
- One version for every crate and the npm package, set in `Cargo.toml` and `clients/js/package.json`. `wenmar-vin`, `wenmar-vehicles` and `wenmar-open-turso` can be published to crates.io.
- `mise run js` builds and tests the npm client. `mise run release-check` checks that the versions agree and the changelog has an entry, and runs `cargo publish --dry-run` and `npm pack --dry-run`.
- A release workflow: a `v*` tag on `main` publishes the three crates and the npm package through trusted publishing, with no stored token, and creates a GitHub release. `docs/releasing.md` is the runbook.
- Each release has the `wenmar-open` command-line tool built for macOS (arm64, x86_64) and Linux (x86_64, arm64).
- `docs/integrating.md`: how an application replaces calls to NHTSA's hosted API and a make and model sync job.
- Data releases are no longer marked as the repository's latest release, so `releases/latest` is always a release of the code.
- The website in Wenmar Pro's look: the wordmark, DM Sans and JetBrains Mono served from the site itself, field edges and warnings with enough contrast in both colour schemes, and print that is black on white from either.
- The result page as a spec sheet in short groups, with Copy for the whole sheet.
- Five guides under `/guides`: how to read a VIN, where to find it, the manufacturer code, the model year chart and the check digit, each with a Markdown version.
- Titles and descriptions for what people search, breadcrumbs, Open Graph tags and JSON-LD structured data on the reference pages. Result pages for single VINs carry none of it.
- `robots.txt` states a policy for AI crawlers. `/llms.txt` follows the llms.txt convention, and `/llms-full.txt` is the documentation as one file. `/.well-known/api-catalog` points to the OpenAPI description. `server.json` describes the MCP endpoint to the MCP Registry.
- `open-server`: the MCP endpoint answers protocol revision 2026-07-28, which has no handshake, as well as the earlier revisions.
- `wenmar-open/offline`, a second entry point of the npm package: VIN decoding and the catalog with no network, by the same decoder as the server, compiled to WebAssembly (450 kB) and run over a data file. It has the hosted client's methods, answers and error codes, with three more codes for the data: `no_data`, `data_invalid` and `store_error`. It reads through `node:sqlite` (Node 22.16 and later), `better-sqlite3`, Cloudflare D1, or a store of your own. The hosted client loads none of it.
- `wenmar-open-data`, an npm package holding the data file, published by the monthly data release. Its version is `<schema version>.<YYYYMM>.<rebuild>`, and `wenmar-open` names the schema version it reads as an optional peer.
- `wenmar-open-d1`, a script in `wenmar-open-data` that writes the data file as SQL files for Cloudflare D1.
- `wenmar-open-wasm` crate (not published): `wenmar-vin` and `wenmar-vehicles` behind one JSON call, over a database made of rows the caller has already read.
- `wenmar-vehicles`: `vin_rows`, the rows one VIN needs read through a `Source`, moved from `wenmar-open-turso`, which re-exports it.
- `shop-math` crate (not published): the arithmetic of the shop calculators, with money as whole cents and percentages as whole thousandths of a percent.
- Shop calculators on the website under `/tools`: a parts markup matrix, a labor rate, gross profit, and Canadian invoice tax and tire fees. Each is a form with no script, a result that can be bookmarked and printed, gross profit targets shown with their sources, and a Markdown version of each page. `Tools` is in the header, and the home page, the sitemap and `/llms.txt` list the calculators.
- The Canadian invoice tax and tire fee calculator, at `/tools/canada-invoice-tax`: the GST, HST, PST or QST and the new-tire fees on a repair invoice for each province and territory whose rules have a source, with the rates and their sources shown on the page. The rates are in `data/rates/canada.toml`, which the server's build reads and checks, and a file that is malformed fails the build.

### Changed

- No statement the libraries run binds more than 91 parameters (it was 201), and the two `LIKE` patterns of the catalog's search are cut to 40 characters, as the others already were. Both are limits of Cloudflare D1. The server runs one more small statement for the few manufacturer codes with over 90 schemas in a model year's range; answers do not change.
- Building and testing `clients/js` needs the Rust toolchain: `npm run build` compiles the WebAssembly.

### Fixed

- `open-server`: a result page is no longer answered `304` as a public page, a failed result page is not kept by the browser, and refusals made before a page's handler runs (too many requests, a busy server, an address that is too long) are pages instead of JSON on page addresses.
- `open-server`: a year in a page's address is exactly four digits; a redirect from a make's alias keeps the year; a list that is cut says so; Markdown versions mark trims and engines from this project's own list, as the pages do.
